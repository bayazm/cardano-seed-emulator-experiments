# Reproduce B13 on an isolated Linux host

B13 uses three routed autonomous systems on IX200. AS170 (`10.170.0.71`) produces blocks for A, AS171 (`10.171.0.71`) relays A, and AS172 (`10.172.0.71`) produces for independently generated B. A's nodes list each other as local roots. The baseline AS172 topology has no external roots. Cardano uses TCP port 3001.

## Install and prepare a fresh run

Use Linux x86-64 and the pinned SEED revision `a8d93cd65aace99a454fae44895d41d7e8cd8197`. Follow [installation](install.md) for Docker, standalone Compose, Bash, Python and venv, Git, curl, tar, and checksum tools. The reference versions are Python 3.8.10, Docker 20.10.21 and Compose 1.27.4. Use Cardano Node **11.1.3** and CLI **11.2.3.0** from the same checksum-verified release archive. Use the SEED virtual environment throughout. The B11 setup script accepts only B11.

From the repository root in Bash, set `scenario` to the directory name given in the experiment README. Copy only the launcher's inputs into a private disposable directory. Use a simple absolute path without spaces or Compose metacharacters for the run directory.

```bash
repo="$(pwd -P)"
source_dir="$repo/experiments/$scenario"
run="$(mktemp -d /tmp/b13-run.XXXXXXXX)"
experiment="$run/$scenario"
mkdir -p "$experiment/config"/{network-A,network-B,specs}
cp "$source_dir/blockchain.py" "$experiment/"
cp "$source_dir/config/network-A/"{config.json,topology-node1.json,topology-node2.json} \
  "$experiment/config/network-A/"
cp "$source_dir/config/network-B/"{config.json,topology-node3.json} \
  "$experiment/config/network-B/"
cp "$source_dir/config/specs/"shelley-spec-{A,B}.json "$experiment/config/specs/"
cd "$experiment"
```

At this point run the **Cardano binaries** section of [installation](install.md) in `$experiment`, choosing 11.1.3. Check the archive checksum succeeds before extracting. Use the following explicit generation command once. Choose a bigger margin for a cold image build. The generator uses a new UTC start and ignores the start placeholder in the Shelley specs. It creates both chains' four era genesis files, updates their hash references in the private copies of `config.json`, and writes one producer's credentials per chain under `config/generated/`. An interrupted generation can leave a partial run directory. Start again in a new directory after a partial failure.

```bash
(umask 077; python3 "$repo/scripts/prepare-genesis.py" "$experiment" --minutes 60)
```

Inspect the resulting magic and start fields and compare the Shelley hashes. Both public independent-chain scenarios and node join use an equal start for A and B. A and B should have different Shelley genesis hashes. Alonzo and Conway files can share defaults. Keep the generated genesis and credentials with their databases. See [genesis generation](genesis.md).

```bash
python3 - <<'PY'
import json
from pathlib import Path

for name in ("A", "B"):
    root = Path("config") / f"network-{name}"
    genesis = json.loads((root / "shelley-genesis.json").read_text())
    config = json.loads((root / "config.json").read_text())
    print(name, genesis["networkMagic"], genesis["systemStart"], config["ShelleyGenesisHash"])
PY
```

## Select the peer topology

The prepared experiment is the baseline. Its AS172 topology has no external local roots. For either independent-chain scenario, create the treatment copy immediately after genesis generation and **before compiling either copy**. For staged node joining, use the baseline only.

```bash
baseline="$experiment"
treatment="$run/treatment/$scenario"
mkdir "$run/treatment" &&
  cp -a "$baseline" "$treatment" &&
  cp "$repo/docs/reproducibility/b13-as172-peer-as170.json" \
    "$treatment/config/network-B/topology-node3.json"
diff -qr --exclude=topology-node3.json "$baseline/config" "$treatment/config"
```

The [AS172 template](b13-as172-peer-as170.json) makes AS172 initiate a connection to AS170 at `10.170.0.71:3001`. The comparison should print nothing. Both copies use the same genesis files, hash references and credentials. Leave them paired throughout the run.

## Compile and build

Run one phase at a time on a dedicated Docker VM. Compose project names identify each phase, and SEED uses fixed container names and subnet ranges across phases. Inspect any existing containers and networks before launching. Use a separate VM for parallel execution.

In the preparation shell, define the following helper. It creates a new runtime root, compiles from the selected copy and prints the Compose project and directory to use in other terminals. Run it once per phase.

```bash
compile_phase() {
  cd "$1" || return
  CARDANO_EXPERIMENT_RUNTIME="$(mktemp -d "$run/$2-runtime.XXXXXXXX")" || return
  COMPOSE_PROJECT_NAME="b13-$(basename "$run" | tr '[:upper:].' '[:lower:]-')-$2"
  export CARDANO_EXPERIMENT_RUNTIME COMPOSE_PROJECT_NAME
  (umask 077; python3 blockchain.py amd) || return
  cd output || return
  docker-compose config -q || return
  printf 'Compose project: %s\nOutput directory: %s\nRuntime directory: %s\n' \
    "$COMPOSE_PROJECT_NAME" "$PWD" "$CARDANO_EXPERIMENT_RUNTIME"
  docker-compose config --services
}
```

**Baseline or staged node join.** Run these commands, then use the selected README's startup sequence from the printed output directory. For a paired comparison, run the [verification checks](#check-tcp-and-the-cardano-handshake) and [remove the baseline's Compose resources](#troubleshoot-and-clean-up) before switching to the treatment. Run the transport and handshake probes in both phases if you want a direct comparison. The baseline's probes are explicit connections from the CLI.

```bash
baseline="$experiment"
compile_phase "$baseline" baseline &&
  docker ps -a --format '{{.Names}}' &&
  docker network ls &&
  docker-compose build
```

**Cross-network treatment.** After the baseline is down, or directly for a treatment-only run, compile the copy that already contains the template. Then use the independent-chain README's startup sequence. For either phase, stop if compilation or Compose validation failed, and check subnet overlap before starting services.

```bash
compile_phase "$treatment" treatment &&
  docker ps -a --format '{{.Names}}' &&
  docker network ls &&
  docker-compose build
```

Record the project, output path, and runtime path. For a new shell, enter that phase's output directory and export the printed `COMPOSE_PROJECT_NAME` before running Compose commands. Both phases can start after genesis time. Compare equivalent observation windows and record actual start times. Keep the compiled output and images private because they contain producer credentials.

## Check TCP and the Cardano handshake

Run the checks after both intended endpoints are up. These helpers resolve Compose service IDs from the current project. Execute the probes from the source node so they traverse the emulated route. Run the commands below from the selected phase's `output/`. Set `b_magic` as specified in the experiment README. Local CLI 11.2.3.0 help confirms the `ping` subcommand, `--mode ping`, `--count`, `--network-magic`, and the positional `IP:port` address form. Ping mode negotiates node-to-node versions and sends keep-alive messages. Live probe behavior remains unverified.

The launchers request `netcat-openbsd` and `tcpdump`; the pinned SEED base image declares `iproute2` for `ss`. The Cardano startup command redirects stdout and stderr to `/var/log/cardano-node.log`. These are build and startup inputs. The commands below check availability in the running container.

```bash
a="$(docker-compose ps -q hnode_170_host_0)"
relay="$(docker-compose ps -q hnode_171_host_0)"
b="$(docker-compose ps -q hnode_172_host_0)"

probe() {
  if docker exec "$1" sh -c 'command -v nc >/dev/null'; then
    docker exec "$1" nc -zvw 3 "$2" 3001
  elif docker exec "$1" sh -c 'command -v bash >/dev/null && command -v timeout >/dev/null'; then
    docker exec "$1" timeout 3 bash -c 'exec 3<>"/dev/tcp/$1/3001"' _ "$2"
  else
    printf 'TCP-only probe unavailable in %s\n' "$1" >&2
  fi
  docker exec "$1" timeout 20 cardano-cli ping --mode ping \
    --count 1 --network-magic "$3" "$2:3001"
}

node_log() {
  if docker exec "$1" test -r /var/log/cardano-node.log; then
    docker exec "$1" tail -n 100 /var/log/cardano-node.log
  else
    printf 'Node log unavailable in %s. Checking container startup output.\n' "$1" >&2
    docker logs --tail 100 "$1"
  fi
}
```

For either independent-chain phase, run:

```bash
probe "$b" 10.170.0.71 "$b_magic"
# Positive protocol control using A's magic.
if [ "$b_magic" != 5555 ]; then
  probe "$b" 10.170.0.71 5555
fi

if docker exec "$b" sh -c 'command -v ss >/dev/null'; then
  docker exec "$b" ss -tn
fi
node_log "$b"
node_log "$a"
```

An explicit version-data refusal provides handshake evidence. A timeout or a closed TCP connection is inconclusive about negotiation. The CLI probe is a separate connection. To attribute negotiation or sustained data exchange to AS172's configured Cardano process, observe it before running the probes. Correlate the remote address and port in the connection logs with a capture of the start of a session. For a capture of initial negotiation, replace the independent-chain README's startup command with `docker-compose up -d --scale hnode_172_host_0=0`. In a second shell, enter the same `output/` directory, set `COMPOSE_PROJECT_NAME` to the exact value from the first shell, and start this capture:

```bash
a="$(docker-compose ps -q hnode_170_host_0)"
if docker exec "$a" sh -c 'command -v tcpdump >/dev/null && test -w /captures'; then
  docker exec "$a" timeout 60 tcpdump -i any -nn \
    'host 10.172.0.71 and tcp port 3001' -w /captures/as170-as172.pcap
else
  printf 'Capture unavailable. Use peer-specific node logs if present.\n' >&2
fi
```

Once tcpdump is listening, or if capture is unavailable, start AS172 with `docker-compose up -d hnode_172_host_0` in the first shell. A timeout exit after 60 seconds is expected. The capture is stored under the private runtime root. Use node logs with a peer-specific negotiation event or decode the Cardano node-to-node handshake in the reassembled capture to confirm the configured process's negotiation outcome. If neither source is available, record that outcome as inconclusive. TCP traffic and a successful standalone ping establish reachability and probe negotiation respectively.

## Check block production and synchronization

```bash
tip() {
  docker exec "$1" cardano-cli query tip --socket-path /cardano/node.socket \
    --testnet-magic "$2"
}
date -u
tip "$a" 5555
tip "$relay" 5555
tip "$b" "$b_magic"
```

Repeat after genesis and during block production. Compare `block`, `slot`, and `hash` together. For A, show AS170 advancing and AS171 reaching an identical block point after its start. Sample repeatedly and match a relay tuple against a point previously seen on the producer. For A versus B, record advancing tips on each side and compare hashes at overlapping heights. A verified hash disagreement at the same stable height shows divergent history there. Sample lag, different tip heights, and `syncProgress` by itself leave the chain comparison inconclusive. Keep notes and any captures in the private run directory.

## Troubleshoot and clean up

If a binary is missing, check the release path and architecture. For routing problems, inspect Compose service status, the SEED routers and `docker exec "$b" ip route`. For an absent socket, use `node_log` on the intended container, then check genesis time, hashes, credential paths and build status. Inspect `docker-compose config` for the database bind sources. If a fixed name or subnet collides, finish the conflicting run or use a separate VM. See [operations](operations.md) and [troubleshooting](../troubleshooting/README.md).

From the selected project's `output/`, check the active project with `printf '%s\n' "$COMPOSE_PROJECT_NAME"` and confirm its services with `docker-compose ps`. Run `docker-compose stop` to preserve its containers and state. To release that project's fixed container names and networks for a paired run, use `docker-compose down` from the same project after checking its targets. The bind-mounted databases and captures remain in the run directory.
